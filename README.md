# Пилот: seed-режимы для перекрёстной проверки (iGSM-подобные задачи)

Проверяем гипотезу: если обучить одну модель с «режимами» z (4 фиксированных кода или непрерывный z)
и winner-takes-all, то режим j находит ошибки режима i лучше, чем режим i сам, и итоговая
точность «решение + проверка» растёт при сопоставимом pass@1 и равном бюджете.

## Запуск (одна команда)

```bash
pip install -r requirements.txt     # нужен torch с CUDA
bash run_pilot.sh                   # бюджет 11 часов от старта
```

- Сначала на переднем плане идёт **предполётная проверка** (5–10 минут): по крошечной версии каждой задачи
  (обучение всех типов, сбор ошибок, этап 2, оценка, шум, отчёт). Если она упала, ночь не тратится:
  смотрите `runs/pilot/logs/pf_*.log`.
- Потом основной прогон уходит в фон (`nohup`), терминал можно закрыть.
- Утром: **`runs/pilot/report.md`** (+ `R_matrix_*.png`, `pass_at_k_*.png`, `summary.json`).

Полезное:

```bash
cat runs/pilot/STATUS.md            # что сейчас идёт, сколько осталось
tail -f runs/pilot/run_all.log      # общий лог
tail -f runs/pilot/logs/train_C_fix.log
kill $(cat runs/pilot/run_all.pid)  # остановить всё
bash run_pilot.sh                   # та же команда продолжает с места остановки
```

Другой бюджет времени: `bash run_pilot.sh 9`. Дополнительные флаги передаются в `pilot.run_all`,
например `bash run_pilot.sh 11 --op_max 12` (пропустить подбор сложности) или `--tokens 2e9`.

## Диск (лимит 40 ГБ)

Данные **не хранятся**: задачи генерируются на лету в воркерах DataLoader (~1 мс на задачу,
10 воркеров на GPU), поэтому цикл «шард → обучение → удалить» не нужен. На диске только
чекпоинты (~90 МБ на модель, промежуточный `last.pt` ~270 МБ удаляется в конце), массивы оценки
и логи — ожидаемо 2–4 ГБ. Оркестратор не запускает новые задачи, если папка прогона подходит к 38 ГБ.

## Что происходит за ночь

| фаза | что | GPU |
|---|---|---|
| preflight | крошечные версии всех задач | ~5–10 мин |
| калибровка | 4 коротких baseline (op_max = 6, 9, 12, 15; 0.25B токенов) → выбирается op_max, где точность ≈ 0.5; замер скорости обучения, WTA и генерации | ~30–40 мин |
| план | максимальный бюджет T (0.5–3B токенов), при котором симуляция расписания укладывается в оставшееся время | — |
| этап 1 | A, A′ (равные FLOPs), C_fix, C_cont, D_fix, D_cont — одинаковая инициализация и порядок данных | основная часть |
| ошибки | A (финал и чекпоинт на 1/3) решает отдельный пул задач → естественные ошибки | ~10 мин |
| этап 2 | C_fix2, C_fix2u, C_cont2, A_RFT — WTA по правильности собственных решений | ~1 ч каждая |
| оценка | 12 методов (вкл. B_fix / B_cont — шум в весах A), ID и OOD по 2000 задач | ~10–20 мин каждая |
| отчёт | report.md с вердиктом по заранее зафиксированному критерию | — |

Задачи раскладываются по 4 GPU по критическому пути; обучение занимает GPU целиком, оценки и
этап 2 (в основном генерация) идут по две на GPU.

## Методы

| имя | что это |
|---|---|
| A | baseline, T токенов |
| A′ (Aprime) | baseline, T·(1+K/3) токенов — те же FLOPs, что у WTA |
| B_fix / B_cont | веса A + гауссов шум (4 фиксированных вектора / свежий шум на генерацию), σ и τ подбираются на val |
| C_fix / C_cont | FiLM-модуляция от z после каждой нормализации + relaxed WTA (K=4) |
| D_fix / D_cont | то же, но обычный loss со случайным z (контроль: использует ли модель z без WTA) |
| A_RFT | A + этап 2 без режимов (4 сэмпла, обучение на правильных) — контроль этапа 2 |
| C_fix2 / C_cont2 | этап 2: побеждают режимы, решившие верно, вес 1/\|W\| (бонус за уникальный успех) |
| C_fix2u | этап 2 с равными весами 1/K — контроль бонуса |

## Метрики (раздел «кто кого проверяет»)

- Для каждой задачи каждый режим i даёт решение; каждый режим j проверяет его **в чистом контексте**.
- Протокол 1: обученный проверяющий читает решение → P(ошибка) и номер первого ошибочного шага.
  Порог подбирается **отдельно для каждой ячейки (i, j)** так, чтобы FPR ≈ 5% (перекрёстная подгонка по
  двум половинам задач), поэтому TPR на диагонали и вне её сравнимы.
- Протокол 2: проверяющий решает сам и сравнивает ответы / значения шагов.
- Итоговые процедуры: maj@4, голосование, взвешенное самопроверкой / перекрёстной проверкой,
  «замена ответа при тревоге» (с подсчётом исправленных и испорченных).
- Только **естественные** ошибки моделей; доверительные интервалы — парный бутстрап по задачам
  (у всех методов одинаковые тестовые задачи).

Критерий успеха (раздел 1 отчёта): pass@1(X) ≥ pass@1(R) − 0.03; TPR вне диагонали − на диагонали > 0;
«голосование + перекрёстная проверка» у X лучше «голосования + самопроверки» у базы R того же бюджета
(для этапа 1 база — A′, для этапа 2 — A_RFT, для шума — A). Оба CI должны исключать 0.

## Задачи

`pilot/igsm.py` — собственный генератор в духе iGSM (не оригинальный код): иерархия из 4 уровней
(город → здание → помещение → предмет), явные параметры «в каждом A есть N B» (константы или выражения
через другие параметры), неявные «всего C в каждом A» (сумма произведений по иерархии), арифметика по
модулю 23, отвлекающие параметры. op — число арифметических операций в нужной части графа.
Решения в двух стилях: прямой (случайный топологический порядок) и обратный (план «need … : …» от
вопроса, затем вычисление). Проверочные данные: верные решения и решения с внесённой ошибкой
(операция, параметр, арифметика, константа, слагаемое суммы), ошибка распространяется дальше.
Задачи делятся по хешу текста: train / natural / val / test не пересекаются.

## Решения, принятые при реализации (стоит знать при чтении результатов)

- **Балансировка WTA для фиксированных кодов.** Без неё один код выигрывает почти всё с первых шагов
  (видно в тестах). Поэтому победители назначаются с ёмкостью 1.25·B/K на код в батче (по относительному
  loss). Отключается `--balance 0` в `pilot.train`.
- **Relaxed WTA стохастически:** победитель с вероятностью 1−ε, иначе случайный проигравший (тот же
  ожидаемый градиент, но один проход назад). ε отжигается 0.5 → 0.05 за первые 20% обучения.
- Loss решения только на токенах решения, loss проверки только на вердикте; loss нормирован на пример.
- Этап 2 использует естественные ошибки A для проверочных данных у всех вариантов (одинаково).
- Модель: 12 слоёв, d=384, 6 голов, RoPE, свой словарь (~260 токенов) → 21.3M параметров ядра +
  1.2M на FiLM.

## Структура

```
run_pilot.sh            одна команда
pilot/igsm.py           генератор, решения, внесение ошибок, проверка решений
pilot/model.py          GPT + FiLM(z), генерация с KV-кешем
pilot/data.py           данные на лету
pilot/train.py          этап 1 (base / wta / mean × none / fix / cont), резюмирование
pilot/collect.py        естественные ошибки
pilot/stage2.py         этап 2 (WTA по правильности)
pilot/evaluate.py       оценка, матрица «кто кого проверяет», шум в весах
pilot/metrics.py        метрики
pilot/report.py         отчёт
pilot/run_all.py        оркестратор: preflight → калибровка → план → расписание на GPU → отчёт
tests/test_pipeline.py  тесты на CPU: генератор/проверка, метрики на синтетическом агенте
```

Тесты: `python3 -m tests.test_pipeline`.

# Фаза 0: Qwen3-1.7B без обучения

Перед обучением режимов на настоящей модели замеряем, что дают простые способы получить разнообразие,
и собираем данные для фазы 1. Обучения нет: только генерация и оценка.

## Запуск

```bash
pip install --no-cache-dir vllm datasets huggingface_hub    # vLLM ставит свою версию torch
bash run_phase0.sh
```

Сначала на переднем плане идёт **пробный прогон** (smoke, 10–15 минут на крошечных размерах): он
проверяет загрузку датасетов и модели, все задачи и отчёт. Если он упал, смотрите `runs/phase0/smoke/logs/`.
Потом полный прогон уходит в фон, ожидаемо **1.5–2 часа** с vLLM на 4 GPU. Результат:
**`runs/phase0/report_phase0.md`**.

Без vLLM код сам переключится на HF transformers, но это в несколько раз медленнее.
Повторный запуск той же команды продолжает с места остановки.

## Диск

| что | сколько |
|---|---|
| модель Qwen3-1.7B (кеш Hugging Face) | ~4 ГБ, один раз |
| датасеты (GSM8K, GSM-Symbolic, MATH) | ~0.2 ГБ, один раз |
| копия модели с шумом | ~4 ГБ, **временно**: одна копия за раз, удаляется сразу после использования |
| результаты (решения, проверки, сжато) | < 0.5 ГБ |
| установка vLLM (если ещё нет) | несколько ГБ: тянет свою версию torch и CUDA-библиотек; `--no-cache-dir` не держит копию в кеше pip |

Нужно примерно 9 ГБ свободного места помимо окружения. Дорожка с шумом остановится сама, если свободно
меньше 6 ГБ (`--min_free_gb`). Если места мало, можно удалить старые чекпоинты пилота:
`runs/pilot/train/*/final.pt` и `runs/pilot/stage2/*/final.pt` (отчёт пилота при этом сохранится).

## Что делается

Тест (~1500 задач): GSM-Symbolic P1/P2 (новые варианты шаблонов GSM8K), MATH уровней 3–4 с числовыми
ответами, синтетика на отложенных шаблонах. Модель в режиме без thinking, τ = 0.7, top-p = 0.8, top-k = 20.

| метод | режимы | проверяющий j |
|---|---|---|
| temperature | 4 сэмпла нейтрального промпта (+4 вторых сэмпла) | один нейтральный |
| strategies | 4 системных промпта: вперёд, с конца, через уравнения, с проверкой | «проверяющий по стратегии j» |
| noise | 4 копии весов с гауссовым шумом (σ подбирается на val: не больше −3 п. точности) | копия j |

Проверка: модель отвечает Yes/No, берём P(No). Порог для каждой пары (решающий, проверяющий) подбирается
на FPR ≈ 5%. Второй протокол — «реши сам и сравни ответы»; на диагонали это второй сэмпл того же режима
(контроль «просто свежая попытка»).

Пул (~12k задач из GSM8K train, MATH train, синтетики): 4 стратегии × 2 решения. Верные решения пойдут
эталонами в multi-reference WTA, неверные — естественными ошибками для обучения проверяющего.

## Пороги (зафиксированы заранее, раздел 1 отчёта)

1. Промпты снижают φ ошибок или долю одинаковых неверных ответов меньше чем на 0.05 → есть что улучшать.
2. AUROC проверяющего по промпту < 0.6 → в фазе 1 нужен обученный проверяющий.
3. Задач, где верна ровно одна стратегия, < 5% → для этапа 2 нужны задачи потруднее.
4. pass@1 источника вне [0.3, 0.85] → сменить задачи этого источника.
5. Промпты значимо улучшают итоговую точность → сравнивать фазу 1 с ними.

Пороги — в `phase0/report.py` (`TH`). Тесты на CPU: `python3 -m tests.test_phase0_report`.

# Фаза 1: обученные режимы на Qwen3-1.7B

Нужна готовая фаза 0 в `runs/phase0` (из неё берутся тест, пул и базовые методы).

```bash
bash run_phase1.sh            # пробный прогон (~30–40 мин) на переднем плане, потом полный (~8.5–10 ч) в фоне
HOURS=13 bash run_phase1.sh   # бюджет времени полного прогона (по умолчанию 12 ч)
```

Статус: `cat runs/phase1/STATUS.md`. Отчёт: **`runs/phase1/report_phase1.md`**. Повторный запуск продолжает
с места остановки, обучение — с последнего чекпоинта.

## Что делается

| шаг | что |
|---|---|
| hard_prep, hard_gen ×4 | задачи потруднее: из пула фазы 0 — решённые ≤ 6 из 8 (ещё 8 решений), MATH train уровня 5, синтетика на 6–10 шагов |
| build | эталоны: правильные решения, сгруппированные по структуре (набор чисел, Жаккар ≥ 0.8), не больше 4 на задачу; 6000 примеров для проверяющего Yes/No (половина — естественные ошибки); отложенный val (600 задач, не участвуют в обучении); набор для этапа 2 (успех базовой модели 10–80%) |
| train ×6 | LoRA r=32 + FiLM (только масштаб, 4 кода) на всех вариантах: `sft1`, `sftmulti`, `filmmean`, `wta1`, `wtamulti`, `wtabal`. **Каждый обучается ровно 2 часа** (≈ равный compute): данные повторяются в новом порядке, пока не кончится время; расписание LR привязано ко времени. Loss = loss решений + 0.4 × loss проверки, каждый нормирован отдельно |
| eval ×6 | каждый режим экспортируется в обычный чекпоинт Qwen3 (LoRA слита, FiLM вшит в веса RMSNorm) → vLLM: val и тест по 2 решения на режим + матрица проверки Yes/No |
| select | на val, по правилу из фазы 1: наименьшая корреляция ошибок среди вариантов с pass@1 ≥ sftmulti − 0.02 |
| stage2 ×2 | лучший вариант и контроль `sftmulti`: 2 раунда «режимы решают → обучение на своих правильных решениях с весом 1/\|W\|» (для контроля — обычный RFT); логируется доля задач, решённых ровно одним режимом |
| noise2 | шум в весах с σ ∈ {0.05, 0.1, 0.2} (в фазе 0 до порчи точности не дошли) |
| report | все методы на тех же 1500 задачах теста фазы 0, парный бутстрап |

## Диск

Экспортированные режимы — по ~3.5 ГБ, хранятся только во время оценки одной модели и сразу удаляются.
Режимы экспортируются по одному (`--min_free_gb_all` включает экспорт всех сразу), пик при 4 одновременных оценках ~14 ГБ.
Адаптеры LoRA + FiLM — ~150 МБ на вариант.

## Проверено на CPU

`python3 -m tests.test_phase1_export`: экспортированный режим k даёт те же логиты, что обучаемая модель с
кодом k (расхождение ~1e-6 в float32). Весь конвейер фазы 1 прогнан на крошечной случайной Qwen3.

# Фаза 1: повторы с seed, контроль лишних проходов SFT, LoRA-MCL и ModC

Нужны готовые `runs/phase0` и `runs/phase1`, новой генерации для обучения нет.

```bash
bash run_phase1_seeds.sh      # пробный прогон (~20–30 мин) на переднем плане, потом полный (~13–14 ч) в фоне
```

Статус: `cat runs/phase1_seeds/STATUS.md`. Отчёт: **`runs/phase1_seeds/report_seeds.md`**. Повторный запуск
продолжает с места остановки и пересчитывает отчёт; второй экземпляр на том же каталоге не запустится (`flock`).
`MAX_HOURS` (16 ч) считается от начала каждого запуска: задачи, которые не успеют закончиться за это время,
пропускаются, а отчёт строится по тому, что есть.

| вариант | что | бюджет |
|---|---|---|
| `wta1`, `wtabal`, `sftmulti` | как в фазе 1 | 2 ч |
| `sft1_eq` | эталоны `wta1`, токены `wta1` того же seed, своё полное расписание LR; главный контроль на лишние проходы | ~1 ч |
| `sftmulti_eq` | SFT-multi с ограничением по токенам: снимок `sftmulti` на токенах `wta1` (seed 0), LR в момент снимка — в отчёте; дополнительный контроль | часть запуска `sftmulti` |
| `loramcl` | 4 отдельные LoRA r = 32 без FiLM, один эталон, relaxed WTA: каждый пример проходит через все адаптеры с весом 1−ε у победителя и ε/3 у остальных, ε = 0.05 | 2 ч |
| `modc` | ModC с метками промптовых стратегий: одна LoRA, `[Mode k]` в начале входа, эталон стратегии k учит режим k (до 4 эталонов на задачу) | 2 ч |
| `sftmodc` | эталоны `modc` без префиксов и режимов, контроль для `modc` | 2 ч |

Ещё один seed со всеми вариантами в том же каталоге: `bash run_phase1_seeds.sh --seeds 0,1,2,3`. Готовое не
пересчитывается, а отчёт сам находит новые seed.

Seed: 0, 1, 2. При seed 0 `wta1`, `wtabal`, `sftmulti` берутся из `runs/phase1` без перезапуска. Оценка только
на тесте: 4 режима или сэмпла × 2 решения и проверка Yes/No; файлы, где ID задач не совпадают с тестом, отклоняются.
Отчёт: среднее ± SD по seed и парный бутстрап для pass@1, maj@4, pass@4, φ и доли одинаковых неверных ответов
против `sft1_eq`, `sftmulti`, `sftmulti_eq` и стратегий фазы 0; для `wta1` и `wtabal` ещё против `loramcl` и
`modc`; для `modc` ещё против `sftmodc`.

Диск: режимы экспортируются по одному, так что на одну оценку приходится ~3.5 ГБ, плюс адаптеры без моментов Adam,
всего ~5 ГБ. Ожидаемый пик ~19–21 ГБ. Если места мало, оценки ждут, пока оно освободится, но эта проверка опирается на
свободное место, которое сообщает ОС: при квоте на томе она не видит настоящий лимит, поэтому следите за ним сами.

Тест на CPU (~6 мин): `PYTHONUTF8=1 python3 -m tests.test_phase1_seeds`.

# Фаза 1: равное число обучаемых параметров (wta1 против LoRA-MCL)

Нужен готовый `runs/phase1_seeds`: варианты r = 32 тех же seed берутся оттуда без перезапуска.

```bash
bash run_phase1_rank.sh       # пробный прогон (~10–15 мин) на переднем плане, потом полный (~3–3.5 ч) в фоне
```

Статус: `cat runs/phase1_rank/STATUS.md`. Отчёт: **`runs/phase1_rank/report_rank.md`**. Повтор запуска продолжает
с места остановки, как у `run_phase1_seeds.sh`; обучение после остановки продолжает и RNG назначения режимов, и счётчики
долей режимов. Правило alpha, модель, `--max_tokens` и `SEEDS_RUN` закреплены за каталогом: с другими значениями
запуск откажется. Пути задаются только переменными `OUT`, `SEEDS_RUN`, `P0`, `P1`, а не аргументами.

| вариант | что | параметров | сравнивается с |
|---|---|---|---|
| `wta1_r128` | `wta1`, LoRA r = 128, alpha 128 | 147.0M | `loramcl` (4 × r = 32): 139.5M |
| `loramcl_r10` | `loramcl`, 4 LoRA r = 10, alpha 35.8 | 43.6M | `wta1` (r = 32): 42.5M |

Seed 0 и 1, обучение 2 ч, оценка как в `phase1_seeds` (те же seed сэмплирования). Выровнены параметры, но не токены:
LoRA-MCL за 2 ч по-прежнему видит примерно вдвое меньше токенов.

alpha: масштаб alpha / r переносится с r = 32 (alpha 64, масштаб 2) по правилу rsLoRA (Kalajdzievski, 2023):
масштаб ∝ 1 / √r, то есть alpha = 2√(32r). При правиле фазы 1 alpha = 2r масштаб остаётся 2, и при том же LR
обновление адаптера с большим рангом больше. Это правило включается через `--alpha_rule 2r` (только в новом каталоге:
`OUT=runs/phase1_rank_2r bash run_phase1_rank.sh --alpha_rule 2r`).

Диск: во время обучения `last.pt` с моментами Adam (~4.6 ГБ на все 4), после — 4 оценки × 3.5 ГБ и адаптеры ~1.5 ГБ;
пик ~16 ГБ. Тест на CPU (~5 мин): `PYTHONUTF8=1 python3 -m tests.test_phase1_rank`.

# Фаза 1: непрерывный случайный z вместо 4 заученных кодов

Нужны готовые `runs/phase1` и `runs/phase1_seeds`: из них берутся данные и обученные `wta1`, `sftmulti`, `loramcl`
seed 0 для сравнения.

```bash
bash run_phase1_z.sh          # пробный прогон (~15–20 мин) на переднем плане, потом полный (~5 ч) в фоне
```

Статус: `cat runs/phase1_z/STATUS.md`. Отчёт: **`runs/phase1_z/report_z.md`**. Повтор запуска продолжает с места
остановки. Пути задаются переменными `OUT`, `SEEDS_RUN`, `P1`; модель, `--k`, `--greedy` и `--max_tokens` закреплены
за каталогом.

**Обучение** (`--variant wtaz --zdim d`, d = 8, 16, 128, 1024; seed 0, 2 ч, LoRA r = 32 + FiLM, как `wta1`). Вместо
4 заученных кодов каждый пример на каждом шаге берёт 4 свежих z = N(0, I) / √d. Градиент получает z с наименьшим лоссом
(WTA без балансировки ёмкости), исследование eps то же, что у `wta1`, и эталон тоже один на задачу. Внутри FiLM z
умножается на 4 = √16, а первый слой инициализирован как у `wta1` (граница 1/4) при любом d. Тогда при d = 16 это в
точности параметризация `wta1`, только коды свежие, а не заученные, а при любом d W·z стартует с той же дисперсией, и
шаг Adam сдвигает его одинаково. Без этого нормировка /√d вместе с /√d в инициализации PyTorch ослабила бы сигнал z в
√d раз. Число параметров почти не меняется: 42.5M, при d = 1024 на 64K больше. Скрытый слой FiLM — 64 нейрона, так
что при d = 128 и 1024 γ всё равно лежит в семействе размерности ≤ 64.

**Оценка** (`phase1/keval.py`), тест, k = 32 попытки на задачу:

| метод | попытки | жадно (T = 0) |
|---|---|---|
| `wtaz_d*` | 32 разных z, по 1 сэмплу | первые 8 z |
| `wta1`, `loramcl` (seed 0) | 4 режима × 8 сэмплов | каждый режим |
| `sftmulti` (seed 0) | 32 сэмпла | 1 |

Попытка j решается с z_j для всех задач: одна модель на z, у каждой задачи все 32 попытки с разными z. Модель для z
или кода FiLM — это общая выгрузка с влитой LoRA, в которой заново пишутся только 57 весов норм, а остальное
подключается ссылками. Так что новый z стоит секунды и почти не занимает диска. В отчёте:
- pass@k для k = 1…32 (несмещённая оценка; у режимов попытки поровну по режимам) и maj@k;
- для разных z при T = 0: различаются ли ответы. Если нет, модель не использует z;
- насколько лучший из 4 кандидатов z выигрывает по лоссу при обучении;
- парные разности с бутстрапом по задачам.

Время: обучение 2.1 ч, затем 4 оценки z (~1.7 ч), затем 3 оценки эталонов (~1.2 ч); около 5 ч на 4 GPU. Это оценка,
а не замер. Главная неизвестная — 137 запусков vLLM, по одному на каждый z или режим, по ~1 мин каждый, и скорость
генерации. Время каждого z пишется в лог: `grep "unit " runs/phase1_z/logs/keval_wtaz_d16.log`. Если первые z идут
заметно дольше 3 мин, следующий прогон лучше делать с `--k 16`.

Повтор оценки с другим адаптером, данными или настройками сэмплирования в том же каталоге откажется запускаться
(`keval.json`), чтобы не смешать результаты. Диск: пик ~15 ГБ, общая выгрузка пишется сразу двумя файлами без
промежуточной копии. Тест на CPU (~5 мин): `PYTHONUTF8=1 python3 -m tests.test_phase1_z`.

# Фаза 1: многораундовое самообучение — открывает ли модель новые задачи

Нужны готовые `runs/phase0`, `runs/phase1` и `runs/phase1_seeds`: стартовые адаптеры seed 0 и 1 берутся оттуда.

```bash
bash run_phase1_self.sh            # пробный прогон (~20–30 мин) на переднем плане, потом полный (~10–14 ч) в фоне
bash run_phase1_self.sh --seeds 0  # только seed 0 (~6–8 ч)
```

Статус: `cat runs/phase1_self/STATUS.md`. Отчёт: **`runs/phase1_self/report_self.md`** — первый раз после seed 0,
второй в конце. Повтор запуска продолжает с места остановки. Пути задаются переменными `OUT`, `SEEDS_RUN`, `P0`,
`P1`. Модель, число раундов, бюджет обучения и размеры наборов закреплены за каталогом, как и размер и время изменения
стартовых адаптеров и данных: подменённый файл запуск не примет. Seed и цепочки можно добавлять.

**Задачи** (`phase1/spool.py`). Ни у одной нет верного решения в обучении фазы 1:
- **A** — задачи старых пулов, где базовая модель не решила ни одной из 8–16 попыток. В обучении их не было.
  Дубликаты по тексту вопроса, а также вопросы, которые обучение, отбор или тесты уже использовали под другим ID,
  исключены. **Av** — то же, но вопрос был в примерах проверки фазы 1 как «No»; такие задачи идут только в пул, не в hv;
- **B** — новые задачи: оставшиеся MATH train уровней 4–5, затем MATH test уровня 5 (в тесте фазы 0 уровни 3–4) и
  синтетика на 8–13 шагов с новым seed. Если MATH не загрузится из кэша, берётся только синтетика, и отчёт об этом
  пишет. Базовая модель решает каждую 8 раз (~15–20 мин на 4 GPU), отсюда страты:
  B0 — 0 из 8, B12 — 1–2 из 8, B36 — 3–6 из 8 (средние), 7–8 из 8 — отбрасываются.

Трудные (A, B0, B12) делятся по стратам и источникам на **hv** (до 800 задач, ни у кого не попадают в банк; ни один
вопрос hv не встречается в пуле) и пул (до 1800, плюс Av). В пул добавляются до 600 средних, иначе банк первых раундов — несколько сотен задач. **frozen** — 600 трудных
задач пула, на которых стартовая модель без обучения получает ещё 20 попыток.

**Цепочки** (на каждый seed):

| цепочка | старт | попытки за раунд | вес решения в банке |
|---|---|---|---|
| `rft` | `sftmulti` | 4 сэмпла | 1 (обычный RFT) |
| `rftbal` | `sftmulti` | 4 сэмпла | 1 / занятых слотов: каждая решённая задача весит 1 |
| `wta1` | `wta1` | по 1 на каждый из 4 кодов FiLM | 1/\|W\|; решение учит режим, который его нашёл |
| `loramcl` | `loramcl` | по 1 на каждый из 4 адаптеров | как у `wta1` |
| `swap` | `sftmulti` | — | финальный банк `wta1` с весом задачи 1, без режимов |

`rft` и `rftbal` используют один раунд 0. `rftbal` — честный контроль: от `wta1` он отличается только режимами, а вес
задачи тот же. `swap` отделяет «режимы нашли лучшие данные» от «режимы лучше на них учатся».

**Раунд** (`phase1/selftrain.py`). Модель решает пул, 4 попытки на задачу. Верные решения с ответом в `\boxed{}`
попадают в банк: 4 слота на задачу (режимы или 4 сэмпла раунда), в слоте хранится последнее допущенное решение.
Следующая модель учится заново от стартового адаптера (как в STaR и ReST-EM, Adam с нуля) на всём банке:
- шагов не больше 300 и не больше 2 проходов по банку;
- P = 16 задач на шаг, все решения задачи в одном шаге;
- LR 1e-4 (у FiLM в 5 раз больше, как в фазе 1), без примеров проверки;
- расписание LR идёт по шагам. Лимит 2 ч на раунд — только страховка: если он сработает, отчёт пометит раунд как
  недоученный.

Значит, состояние опыта — только банк. У LoRA-MCL каждая строка идёт только через адаптер своего режима
(`--variant fixed` с `lora_modes`). Раньше `stage2.py` построил бы для LoRA-MCL одну LoRA с FiLM; теперь
`phase1.train` от такого отказывается, а `stage2.py` передаёт коды FiLM из адаптера.

6 раундов: модели M_0…M_5 ищут решения в пуле, M_1…M_6 учатся. Отложенные задачи hv и тест оцениваются у M_0, M_2,
M_4 и M_6. На hv у M_0 и M_6 16 попыток (по 4 на режим), у M_2 и M_4 по 4. На тесте 4 попытки.

**Главная метрика зафиксирована до запуска:** pass@16 на hv у M_6, `wta1` − `rftbal`, парный бутстрап по задачам.
Вывод «wta1 лучше» требует трёх условий:
- общий по seed интервал выше 0;
- у каждого seed разность > 0;
- разность не меньше 0.02.

Пока нет результатов всех запланированных seed, вывод помечен как предварительный. У каждого seed свой интервал.
Отличие `rftbal` от `wta1` не только в режимах: у них разные стартовые адаптеры фазы 1, так что это сравнение
полных методов, а не одних режимов. Поэтому в отчёте есть и разность изменений (M_6 − M_0).

Остальное в отчёте — вторичное и разведка:
- pass@1, pass@4, maj@4;
- тест;
- сравнения с `rft` и LoRA-MCL;
- открытия на пуле против frozen;
- банк по раундам;
- дополняют ли режимы друг друга: одна попытка каждого режима против 4 попыток одного, исключительные решения,
  точность по режимам;
- `swap`;
- страты hv.

`audit_sample.md` — выборка первых открытий без названий методов для ручной проверки: фильтр `\boxed{}` не защищает от
угаданных ответов.

**Время.** Это оценка, а не замер: 850 решений/мин на GPU, запуск vLLM ~1 мин, выгрузка ~2 мин, раунд обучения ~15 мин.
По ней план занимает ~10 ч на два seed, seed 0 отдельно ~6 ч. Главная неизвестная — скорость генерации на трудных
задачах: у них решения длиннее. Seed 0 идёт первым (у его задач выше приоритет), seed 1 занимает освободившиеся GPU. Если seed 1 не успевает к
`MAX_HOURS` (16 ч), его задачи пропускаются, а отчёт по seed 0 уже готов. План печатается при запуске. Его константы
можно поправить по замерам, например `--gen_per_min 600 --train_min 20` (по логам `runs/phase1_z`:
`grep "unit " runs/phase1_z/logs/keval_*.log`). Сокращать лучше по порядку:
1. `--chains rftbal,wta1,loramcl`;
2. `--rounds 4`;
3. `--seeds 0`.

Диск: одна выгрузка (3.5 ГБ) на каждую идущую генерацию, промежуточные адаптеры удаляются после своей генерации; пик
~16 ГБ. Тест на CPU (~5–10 мин): `PYTHONUTF8=1 python3 -m tests.test_phase1_self`.
